# Turso setup and deployment (generic — same steps for every deployment)

Architecture: Browser -> TanStack Start server functions -> Turso/libSQL.
The browser never connects to the database; all credentials stay on the server.

One client = one Turso database + one app deployment. The source code is the
same for everyone; only the environment variables differ. No client data,
credentials or shop details live in the code.

## 1. Create and initialise a database

```bash
turso db create <db-name>
turso db show <db-name> --url          # -> TURSO_DATABASE_URL (libsql://...)
turso db tokens create <db-name>       # -> TURSO_AUTH_TOKEN

TURSO_DATABASE_URL=... TURSO_AUTH_TOKEN=... bun run db:migrate
```

- Migrations live in `turso/migrations/` and run in filename order.
- Applied files are recorded in `_migrations` (with a checksum); re-running is
  safe and skips applied files. An edited, already-applied file is refused.
- Never edit an applied migration — add a new numbered file.
- The only seeded row is the generic default `shop_settings`. No products,
  customers, invoices or users are created.

Local testing: `file:local.db` works for `db:migrate` only. The running app
talks to the database over HTTP, so for a local app test run a local libSQL
server (`sqld`, e.g. `http://127.0.0.1:8080`) or use a Turso test database.

## 2. Environment variables (all server-only)

| Variable | Purpose |
|---|---|
| `TURSO_DATABASE_URL` | the client's database URL |
| `TURSO_AUTH_TOKEN` | the client's database token |
| `SESSION_SECRET` | 32+ random characters, different for every deployment |

None of these may have a `VITE_` prefix; the browser never receives them.
Generate a secret with `openssl rand -base64 48`.

## 3. Deploy (Vercel)

1. Import the GitHub repository (same repo for every client).
2. Add the three variables above in Production (and Preview if used), and
   also `NITRO_PRESET=vercel` (not a secret; the build's default target is
   Cloudflare Workers, so this tells it to produce Vercel output).
3. Deploy. Build command `npm run build`.
4. Open the site, go to sign-up and create the client's owner account — the
   first account on a clean database becomes the admin; later accounts get no
   store access.
5. In Settings, enter shop name, address, phone, GSTIN, invoice prefix and
   receipt footer.
6. Make one test sale, print the receipt, then void the test by agreement or
   start the client on a fresh database.

To repeat for the next client: new Turso database, run `db:migrate`, new
Vercel project from the same repo with that client's variables, first sign-up.

## Stored value formats

| Kind | Stored as |
|---|---|
| Money | integer paise (Rs 12.34 = 1234) |
| Tax / GST rates | integer basis points (18% = 1800) |
| Timestamps | ISO-8601 UTC text |
| Dates | `YYYY-MM-DD` text |
| Yes/no | 0 / 1 |
| Lists (allowed GST rates, import errors) | JSON text |
| Ids | UUID text generated by the server |

The app converts these back to rupees/percent before anything reaches the screen.

## Sign-in

- Login lasts exactly 30 days from sign-in (not extended by use), survives
  refresh and browser restart, and is stored only in a secure HTTP-only cookie.
- Sign out and password change revoke sessions on the server immediately.
- Passwords: PBKDF2-SHA256, random salt per user.
- Password recovery: the owner changes it in Settings. No email service.

## Automatic housekeeping (no scheduler needed)

- Product-import logs older than 30 days are deleted each time a new import
  is recorded. Nothing else is touched.
- Expired or signed-out login records are deleted whenever someone signs in.

## Invoice numbers

Invoice numbers are never cut short. When the next number no longer fits the
"Number padding" digits in Settings, billing stops with a clear message until
the admin raises the padding.

## Backups

Turso keeps point-in-time restore history (length depends on the plan). For an
extra copy, run `turso db shell <db-name> .dump > backup-YYYY-MM-DD.sql`
weekly and keep it off-site. Restore by creating a new database from the dump
(or from a point in time) and pointing `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN`
at it.

## Locked-out owner (developer only — never exposed on the website)

```bash
TURSO_DATABASE_URL=... TURSO_AUTH_TOKEN=... bun run admin:reset-password owner@shop.com
```

Prompts for a new password (or reads `NEW_PASSWORD`) and signs that user out everywhere.
